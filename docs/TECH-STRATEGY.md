# 技术选型与服务边界战略（面向未来）

> 面向对象：不写代码的决策者 + 接手开发的 AI 会话。
> 目标：**不再碎片化**。每类活归一个语言，边界用 API 说话。

---

## 一、现状（事实，不是评判）

| 项目 | PHP | Python | JS/TS |
|---|---|---|---|
| OpenFlow | **824** | 17 | 13 |
| PayFlow | **121** | 0 | 1 |
| inFlow | 0 | **151** | 1 |
| MFlow | 5 | **212** | 18 |
| UserLoop | 0 | **47** | 0 |
| Webs Flow | 1 | 0 | **43** |

结论：**已经是多语言并存**。问题不是"PHP 落后"，而是**没有统一约定**——同样的活，不同产品用了不同语言。

---

## 二、分层选型（唯一约定）

| 层 | 干什么 | 用哪个 | 为什么 |
|---|---|---|---|
| **表现层**（页面/SEO/CMS/后台表单） | 官网、文章、落地页、后台 | **PHP（保持）** | 已 824 文件 / 127 项测试在跑；rsync + Apache 就能部署（30 分钟上线是卖点）。**不重写。** |
| **AI / 数据 / Agent / 爬虫** | 情报采集、画像、自动化、模型编排、数据管道 | **Python** | 三个产品已在用；AI 生态最全；AI 写 Python 最稳 |
| **边缘 / 前端交互 / 新后台 UI** | Cloudflare Workers、页面交互、可视化后台 | **TypeScript** | CF Workers 本身就是 JS 运行时（已在用）；**类型检查能挡住 AI 写出的低级错误**；前后端边缘一套语言 |
| **基础服务**（可选，遇到瓶颈再上） | 事件总线、网关、高频爬虫 | **Go** | 单文件部署、并发强 |
| **其他** | — | **Rust 暂不考虑** | 迭代慢、AI 出错率高，此阶段负收益 |

**一句话口诀**：
> 页面/SEO → PHP　｜　AI/数据/爬虫 → Python　｜　边缘/前端/新 UI → TypeScript　｜　拿不准 → 维持现状，别为换而换

## 三、目标形态

```
浏览器
  │
  ├─ 边缘层   Cloudflare Workers · TypeScript        缓存/图片/静态资产/轻鉴权（已就绪：r2-assets/img-opt/api-cache/r2-media）
  │
  ├─ 表现层   PHP（OpenFlow·PayFlow 保持）            官网·CMS·后台·落地页   ← 只通过 HTTP API 调下面
  │
  ├─ 服务层   Python · FastAPI                        inFlow 情报 / UserLoop 全域数据 / MFlow 内容分发（当前形态）
  │
  └─ 数据层   JSON → SQLite → Postgres/Turso         对象存储 R2；按"数据量/并发写"触发升级
```

**铁律**：服务之间**只准通过 API 说话**，绝不共享数据库。
（现有基础很好：116 个 API 端点 + MCP + 127 项测试。）

## 四、API 契约模板（新服务照这个写）

```http
POST /api/v1/<service>/<action>
Authorization: Bearer <API_KEY>            # 或 HMAC: X-Signature + X-Timestamp
Content-Type: application/json

{ "payload": { ... } }
```

响应（成功/失败统一形状）：
```json
{ "ok": true,  "data": { ... }, "meta": { "ts": "..." } }
{ "ok": false, "error": { "code": "INVALID_INPUT", "message": "..." } }
```

约定：
1. **幂等**：写操作带 `idempotency_key`，重放不重复生效
2. **超时**：跨服务调用设 2–5 秒超时，失败**旁路**（不能拖垮主请求）
3. **签名**：出站事件用 HMAC（参考 `plugins/insight-flow/` 的实现）
4. **版本**：路径带 `/v1`，破坏性变更开 `/v2`，不原地改

## 五、渐进迁移路线（不建议大爆炸重写）

| 阶段 | 做什么 | 明确不做 |
|---|---|---|
| 1（现在） | 本文档 + 服务边界 + API 契约定为约定 | 不动代码 |
| 2 | **新功能只用新约定写**：AI/数据 → Python；边缘/交互 → TS；OpenFlow 只加"薄适配层" | 不回头重写老功能 |
| 3 | 把 OpenFlow 里"不像 PHP 该干"的部分抽出：**爬虫 / AI 编排 / 事件流** → 独立 Python 服务，PHP 调 API | 不追求一次抽干净 |
| 4 | 数据层升级：JSON → SQLite → Postgres/Turso（按数据量触发） | 不为时髦迁库 |
| 5（可选） | 后台重交互界面 → 逐步 TS 化 | 不做大爆炸 |

---

## 六、什么时候**不要**迁

- 只有页面 + 表单 + 支付的产品：PHP 够了
- "能跑且没人抱怨"的功能：**不动它**是最好的决定
- 纯为了"技术看起来更现代"：不值当（你会付出重写成本，用户看不到任何变化）

---

## 七、决策清单（每次开新功能前问三句）

1. 这活属于哪层？（页面 / AI 数据 / 边缘前端 / 基础服务）
2. 它要不要跟别的服务说话？要 → 先定 API 契约（第四节模板）
3. 现有服务里有没有能直接用的？有 → 调 API，别重造
