# 技术路线 · 说人话版

> 这份取代 `AUDIT-08` 做"能读的那一份"（`AUDIT-08` 留着当证据附录，里面是实测数字和代码位置）。
> 只回答两个问题：**① 现在这版，为一人公司该升级什么。② 中型和大型两个分支怎么开发。**

---

## 一句话

现在这套系统有一个**"抄写员的毛病"**：每记一条访客行为，它要先把最近一万条整本抄一遍。
这个毛病跟用什么数据库无关，换 SQLite、换 PostgreSQL、换 ClickHouse 都治不好，
**而它正在你最需要系统撑住的时刻拖垮你。**

先治这个。别的都往后排。

# 第一部分 · 现在这版该升级什么（面向一人公司）

## 1. 毛病是什么

想象一个记账本。来了一个访客点了一下，系统本该做的事是：**在本子最后添一行。**

它现在做的是：

> 先把最近一万行**整本抄一遍**（还要逐行翻译一次），
> 再添上你这一行，
> 然后把**最后 200 行又重抄一遍**（其中 199 行是重复的，白抄）。

实测（在生产量级的 52 万条数据上）：

| | 耗时 | 内存 |
|---|---|---|
| 现在：记一条访客行为 | **0.134 秒** | **26 MB** |
| 本该：直接添一行 | 0.0007 秒 | 几乎为 0 |
| | **多做了 180 倍的无用功** | |

**批量上报更糟**。正常访问一个页面，前端会一次上报十几二十条行为。
系统的处理方式是**逐条走一遍上面的流程**——也就是把那一万行**抄 20 遍**：

> **一次正常的页面上报 = 2.6 秒。**

## 2. 为什么这对一人公司是致命的，而不是"以后再说"

一人公司的服务器是便宜单机，同时能处理的请求数很有限（几十个）。平时确实没事。但：

> ### 你的内容火了的那一刻，正好是系统最容易垮的那一刻。

一篇文章上了热门，几百人同时进来。每人上报要占住一个处理位 2.6 秒，
处理位很快占满，后面的人页面打不开、埋点全丢——
**你终于等到流量了，而系统在这一刻掉链子。**

对一人公司来说这不是性能问题，是**生意问题**：你没有运维、没有第二台机器、
没有人在半夜盯着，爆发只有一次机会。

**还有一点很重要**：这个毛病**不是"数据攒多了才出现"**。
它读的窗口是固定的一万条，所以**从第一万条事件起，成本就一直是满额的**，
现在生产已经 52 万条了。它不会先给你预警再撞墙——**它一直在那**。

> 顺带说明为什么 `EVOLUTION.md` 没抓住这个：那份文档认为要等事件超过 500 万才需要升级。
> 但这个开销跟数据量无关，所以那条触发线量错了对象。
> 另外，事件表**早就搬到 SQLite 上了**——搬完性能并没有变好，
> 因为病不在"存在哪"，在"每次怎么取"。

## 3. 第二个毛病：AI 在替你烧钱，而你看不见

这是一个按 AI 调用花钱的产品，但现在：

| 情况 | 说明 |
|---|---|
| **有一个对外开放的 AI 问答接口，谁都能调，没有次数限制** | 任何人写个循环，就能把你这个月的 AI 预算烧光，顺便把服务器处理位全占住。**这是我上一轮自己写的（站点 Agent 客服），当时只想着"能答"，没想它是个花钱的公开接口。** |
| **所有 AI 调用统一等 90 秒** | AI 供应商一慢，一个请求就占住一个处理位 90 秒。几个并发就能让整站打不开。 |
| **没有任何花费统计** | 你不知道哪个功能花了多少钱，也没法设上限。 |
| **AI 挂了会怎样，没人验证过** | 代码返回了失败标记，但每个用到 AI 的界面是不是都处理了，得逐个核。 |
| **选"Claude"这个供应商大概率是坏的** | 请求格式写错了一个字段位置，Anthropic 的接口应该会直接拒绝。**建议你现在就去后台切到 Claude 试一下**，两分钟能验证。 |
| **AI 变笨了，测不出来** | 57 个测试里只有 2 个碰了 AI。"大脑给的建议质量下降"目前没有任何测试会报警。 |

对一人公司，**"这个月 AI 花了多少钱"比"数据库能存多少行"重要得多**。
`EVOLUTION.md` 通篇没提这件事。

## 4. 一人公司该升级的四件事（按这个顺序）

| 顺序 | 做什么 | 改完什么样 | 工作量 |
|---|---|---|---|
| 1 ✅ | **治抄写员毛病**（已做，见下方实测） | 记一条：0.134 秒 → **0.0003 秒**<br>批量上报：2.6 秒 → **0.0013 秒**<br>内存：26 MB → 6 MB（整个进程） | 已完成 |
| 2 ✅ | **给 AI 装电表和保险丝**（已做，见下） | 每个功能花多少钱看得见；<br>公开接口加次数限制；<br>每天花费到顶自动降级（只查知识库不调模型） | 已完成 |
| 3 | **AI 挂了站点不能跟着挂** | 分档超时（访客界面最多等 3 秒，后台批处理才允许等久）；<br>AI 不可用时每个界面仍能正常显示 | 2–3 天 |
| 4 | **给大脑装体检** | 固定几组输入，检查输出的**结构**对不对（字段齐不齐、动作在不在允许范围、有没有泄露个人信息）——不检查具体文案。<br>让"大脑变笨"变成一个会报警的测试 | 3–5 天 |

第 1 件跟未来走哪条路完全无关，**怎么选都得做，而且现在就在流血**。

同类毛病全仓还有 43 处，多数无害（一个几百条的日志）。逐个判过之后，热路径上的是
**触达频控**和**邮件打开统计**，已随第 1 件一起改完。

### ✅ 第 1 件已完成（2026-08-31）

| 场景 | 改前 | 改后 | 倍数 |
|---|---|---|---|
| 记一条访客行为 | 134.3 ms / 26 MB | **0.34 ms** | 395× |
| 一次页面上报（20 条） | ~2686 ms | **1.30 ms** | 2066× |
| 群发 1000 人的频控开销 | ~168 秒 | **0.26 秒** | 648× |
| 邮件打开追踪一次 | 读写两万条 JSON | **0.22 ms** | — |

改的四处：

1. `CdpSystem::track()` —— 去掉「先读一万条」，直接单行 INSERT。
2. `CdpSystem::countUserEvents()` —— 分群规则里的第二条热路径（每次埋点后都要算），
   从「把一万条读进 PHP 逐条比对」改成带索引的 `COUNT(*)`，并加索引
   `events(uid, event, created_at)`。**这条是修的过程中才发现的**——
   原来单次埋点其实读了两遍一万条，不是一遍。
3. `FrequencyCap` —— 频控迁 SQLite：判断 = 两个索引计数，记录 = 一行 INSERT。
4. `MailCampaign` 打开/点击统计 —— 迁 SQLite 原子累加。
   这里顺带修掉一个**正确性 bug**：老实现的读-改-写在并发下会互相覆盖，
   群发后打开数集中涌入时会**丢计数**，打开率一直偏低。

外加一处顺手的：`EventDictionary::isEnabled()` 是 `track()` 的第一道检查，
原来每条事件都要读一次开关文件，加了请求内缓存。

三处迁移都沿用画像迁移的老规矩：**老 JSON 首次访问自动导入、原文件保留作回滚备份、
SQLite 不可用时回退到原实现**。回归测试见 `tests/track_writepath_test.php`、
`tests/frequency_cap_test.php`、`tests/mail_stats_test.php`；
端到端基准 `php tests/track_e2e_bench.php`。

**判过但不动的**（不在热路径，改了只是徒增风险）：AI 调用日志、转化回传日志、
数据质量记录、隐私请求、社交发布日志、同步日志。
**已知遗留**：直播聊天（`LiveSystem::live_chat_send`）保留 300 条整批写回——
量小不影响性能，但并发下同样有丢消息的可能，等直播真的有人用了再动。

### ✅ 第 2 件已完成（2026-08-31）

后台新增 **AI 用量与预算**（`/xmp/ai-usage`）：今天花了多少、这几天钱花在哪个功能上、
按模型和按天拆开看、以及在哪踩刹车。

**电表**：每次调用记一行——哪个功能、哪个档位、哪个模型、进出多少 token、多久、成没成。
**token 是从供应商响应里读的实测值**；金额按可配单价推算。
单价表**故意默认是空的**——各家单价差几十倍还经常变，内置一份猜的价钱只会给出一个
看起来精确其实是错的数字。没配价的模型只记 token、金额算 0，后台会把这些模型列出来提示补录。

**保险丝**：两层，缺一不可。
- **额度**（`AiBudget`）：全站日成本/日 token 上限，外加访客侧**单独一道更低的闸**，
  这样外部滥用烧不穿站长自己的用量。触顶后站点客服自动降级为仅检索站内知识——
  这条降级本来就在代码里，现在才真的被触发得到。
  上限**默认全是 0（不限）**：合适的数字只有站长自己知道，我不给别人的生产环境塞一个拍脑袋的数。
- **单 IP 限流**：公开的站点客服接口 10 分钟 20 次。只有额度是不够的——
  一个人几分钟就能把全天额度刷爆。

**分档超时**：访客界面 12 秒 / 后台交互 30 秒 / 后台批处理 90 秒，另加 5 秒连接超时。
原来所有调用统一等 90 秒，供应商一慢就能占满 PHP-FPM 让整站打不开。

**顺带修好的三个一直是坏的地方**（都是查代码时发现的，不在原计划里）：

1. **Claude 供应商从来没能用过**：`system` 被塞进了 `messages`，而 Anthropic Messages API
   的 `system` 是顶层参数、`messages` 只接受 user/assistant——选 Claude 会被直接 400 拒掉。
2. **一键生成落地页从来没成功过**：`api/ai-landing.php` 读 `$r['content']`，
   而 `AiCenter::chat()` 返回的是 `text`，没有 `content` 这个键，所以永远返回「AI 生成失败」。
   顺带 `extractJson` 原来只认 `{...}` 不认 `[...]`，而这个接口要的就是数组。
3. **GEO 自动写文绕过了电表**：`geo_ai_call` 自建了一份 curl（自己的 90 秒超时、
   漏掉 Claude 分支、零记账）。这是全站最耗 token 的功能（每篇 4000 max_tokens），
   却一条账都没记。现在统一走 `AiCenter`。

全部 17 个 AI 调用点都打了 `feature` + `tier` 标签，并有测试守着不许漏标。

回归：`tests/ai_budget_test.php`(42) · `tests/ai_provider_shape_test.php`(25)。

# 第二部分 · 中型和大型两个分支怎么开发

## 1. 最重要的一句：不要真的开分支

一个人维护不了三份代码。真分了叉，半年后三份就长歪了，
**每个新功能要做三遍，每个 bug 要修三遍。**

做法是：

> **一份代码，三个开关。**
>
> - 一人公司 = 默认，什么都不开
> - 中型 = 打开"团队"开关
> - 大型 = 打开"多租户"开关

## 2. 中型公司要的不是"能装更多数据"，是"几个人一起用不出事"

这点很容易搞错。3–30 人的公司，事件量跟一人公司**差不了一个数量级**。
他们的痛完全不在数据量上：

| 一人公司的痛 | 中型公司的痛 |
|---|---|
| 没人帮我干活 | 谁能看客户名单，谁不能 |
| 系统在流量高峰时垮 | 谁能改价格、能提现，谁不能 |
| AI 花了多少钱不知道 | 上周谁改了这个价格，查得到吗 |
| — | 一个人管三个品牌站，能不能分开 |

**现状是什么样：**

- **登录这道门修得很好**——190 个后台页面里，有 184 处在检查"登录了没有"。
- **但门后面，所有人的权限基本一样。** 现在有 admin / marketing / sales 三个角色，
  可整个系统里**只有 22 处真的按角色做了判断**。
- **审计日志有，但只有 1 个地方在往里写。** 也就是说"谁改了什么"基本查不到。

> 需要更正 `EVOLUTION.md` 的一条：它写着"多用户角色（roles.json 已支持）、角色/权限矩阵已就位"。
> **这条不成立**——`roles.json` 这个文件根本不存在。做中型分支时别按这个前提排期。

**好消息**：因为登录检查是**统一的一道关卡**（184 处走的是同一个函数），
在那道关卡旁边加一层"这个角色能不能做这件事"，是最省力的改法——
**改一处，190 个后台页面全部生效。**

所以中型分支就是三件事，**都跟数据量无关**：

1. 权限矩阵（在现成的关卡上加一层）
2. 审计留痕（谁改了什么，现在几乎是空的）
3. 多站点（一个人管好几个品牌）

## 3. 大型分支：先想清楚你要做哪种"大"

**这是唯一需要你拍板的事。** 有两种完全不同的"大"，选错了会白干几个月：

| | **A · 一个客户变得很大** | **B · 你有很多个小客户** |
|---|---|---|
| 长什么样 | 1 个站，10 亿条数据 | 1 万个站，每个 10 万条 |
| 像什么 | 盖一栋 100 层的楼 | 盖一万栋一样的小房子 |
| 难在哪 | 地基、电梯、消防<br>（换数据库、分片、拆服务） | 流水线、水电接入、物业<br>（开通、隔离、算成本） |
| 客户是谁 | 一家大公司 | 一万个一人公司 |
| "数据 100% 本地可控" | **做不到了**（都倒进一个大库） | **还在**（各是各的） |
| 要不要换数据库 | 要（PostgreSQL + ClickHouse） | **不要** |
| 你已有的联邦学习 | 没意义（一个大库直接查就行） | **正是它的核心机制** |

**我的判断是 B。** 理由不是技术偏好，是三条**你自己已经定下的东西**：

1. 产品写的是"面向一人公司 / 超级个体 / 创作者"。
   **一万个他们加起来才叫大**——一个一人公司永远不会有 10 亿条数据。
2. 你说过"数据 100% 本地可控"。A 路线要把所有客户的数据倒进一个大库，这句话就没了。
3. 你已经建了**联邦增长智能**（各站匿名贡献经验、互相变聪明）。
   那正是"一万栋小房子共享经验"的机制——**在 A 路线里它没有存在的必要。**

> `EVOLUTION.md` 把 A 和 B 混在同一张表里写了：一行说"每租户独立目录、天然隔离"（这是 B），
> 紧接着几行说"主库换 PostgreSQL、事件走 ClickHouse"（这是 A）。**这两条是打架的，得删掉一条。**

## 4. 好消息：B 路线的技术准备，你已经做完了 90%

这是我这次查代码最意外的发现，值得单独说。

"一个客户一个独立目录"这种改造，通常是最难的，因为"数据放在哪"这个信息
会散落在成百上千个地方，改起来要翻遍全仓。

我数了一下：这个项目里"数据目录"被用了 **861 次**。听起来吓人。
**但它们全都读同一个变量，而这个变量只在一个地方定义**
（`admin/config.php` 里从环境变量读出来，一行 `define`）。

> **也就是说：改那一行，让它"按访问的域名决定用哪个目录"，861 处全部自动跟着走。**
>
> **一天的工作量，多租户就成立了。**

这是这个项目结构上最值钱的一件事。`EVOLUTION.md` 说它"天然隔离"是**说对了**，
但没说清楚为什么这么便宜——所以也就没意识到，
**这意味着大型分支的门票几乎是免费的，根本不需要先做那个几个月的大抽象。**

## 5. 三个档位实际上是这么长出来的

```
                    一份代码
                        │
        ┌───────────────┼────────────────┐
        │               │                │
   一人公司           中型              大型
   （默认）      打开"团队"开关     打开"多租户"开关
        │               │                │
   什么都不开      · 权限矩阵        · 按域名分数据目录
                   · 审计留痕        · 开通流程
                   · 多站点          · 每租户成本核算
                                     · 联邦学习（已有骨架）
```

**现在需要为后两档做的准备，只有一件**：把数据目录那一行改成"可以按域名变"。
**别的都别提前做。**

# 第三部分 · 所以先做什么

| 阶段 | 做什么 | 什么时候 | 为什么是这个顺序 |
|---|---|---|---|
| **一** | 治抄写员毛病 + 给 AI 装电表保险丝 | **现在，1–2 周** | 现在正在流血。跟未来走哪条路无关，**怎么选都要做** |
| **二** | 数据目录改成"按域名可变" | 随时，**1 天** | 一天换来大型分支随时可开。做了不亏 |
| **三** | 权限矩阵 + 审计留痕 | **等有第一个团队客户** | 没有真实团队用，权限怎么分一定是拍脑袋 |
| **四** | 定下走 B 路线，删掉 `EVOLUTION.md` 里 A 的部分 | **纸面决定，现在做** | 不定，后面所有架构决策都没法定形 |

**现在明确不建议做的三件事：**

| 不做 | 为什么 |
|---|---|
| `EVOLUTION.md` 里那个 DataStore 大抽象 | 要改 **1389 处**调用点（文档估的是 87 个文件，低估了一个数量级），几个月工作量。而收益只在**你的用户永远到不了的数据规模**才兑现。真要抽象，等阶段四定完轴，而且形状要换（见 `AUDIT-08` 第四节） |
| ClickHouse / PostgreSQL | B 路线根本不需要 |
| Redis | 现在的瓶颈是"做了 180 倍无用功"，不是"缓存不够"。<br>先把无用功去掉，再看还缺不缺缓存——**很可能就不缺了** |
