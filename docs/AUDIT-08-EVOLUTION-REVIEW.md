# 演进路线复核 · 08（EVOLUTION.md 好不好）

> `docs/EVOLUTION.md` 提出了 Tier 1/2/3 三档演进与两个地基抽象（DataStore / EventSink）。
> 这份不复述它，只做一件事：**把它的每条断言拿去撞代码，判定好不好、该不该照做。**
> 评级：✅ 成立（照做） / 🟡 方向对但形状不对 / 🔴 误判（会带偏）。

## 一句话结论

EVOLUTION.md 的**原则是对的**（换底座不换楼、量化触发、抽象先行），
`Database.php` 是唯一切换点这条也**实测成立**。但它的**诊断错了一层**：

> **它把瓶颈归因于"数据访问散落各处"（一个结构问题），
> 于是开出"加一层 DataStore 抽象"的药方。
> 但实测下来，真正的瓶颈是一个跟存储无关的<b>访问模式</b>——
> 「整批读进内存 → 改一条 → 整批写回去」。
> 事件表<b>已经迁到 SQLite 了，这个模式照样让单条埋点花 134 毫秒、吃 26 MB</b>。**

抽象层不治这个病。把 `allEvents()` 包进 `DataStore::query()`，134 毫秒一毫秒不少；
底下换成 ClickHouse 只会更慢（每次 pageview 变成一次万行网络拉取）。

而且墙**不在 500 万事件**，按 `tests/events_index_bench.php` 里记的生产量级
（约 52 万行），**墙现在就在撞**。

## 二、核心分歧：瓶颈不是"散落"，是"访问模式"

### 证据：单条埋点的真实成本

`lib/CdpSystem.php:51` —— `track()` 的第一件事是 `$events = self::allEvents();`，
而 `$events` 全程**只被用来 append 一条然后整个交给 `saveEvents()`**。
`saveEvents()`（`:158-184`）再把**末尾 200 条**逐条 `INSERT OR IGNORE`。

于是每记一条 pageview，实际发生的是：

```
SELECT … FROM events ORDER BY id DESC LIMIT 10000    ← 拉一万行
json_decode(props) × 10000                            ← 解一万次
array_reverse(10000)
INSERT OR IGNORE × 200                                ← 199 条是空转
```

在 52 万行的表上实测（云端 SSD，生产的宝塔机只会更慢）：

| 动作 | 耗时 | 备注 |
|---|---|---|
| A. `allEvents()` 读一万行 + 解码 + 反转 | **132.2 ms** | 峰值内存 **26 MB** |
| B. `saveEvents()` 末尾 200 条重复 INSERT | 2.1 ms | 199 条 IGNORE 空转 |
| **单事件总开销** | **134.3 ms / 26 MB** | |
| 对照：只 INSERT 1 条（应有成本） | **0.743 ms** | |
| | **放大 181 倍** | |

复现：`php tests/events_writepath_bench.php 520000`（脚本已随本文收进 `tests/`，
灌 52 万行要几十秒，不进 `qa_full` 必跑集）。

### 为什么这条推翻了文档的药方

事件表**早就在 SQLite 上了**——文档设想的 Tier 1→2 存储升级，在这块已经发生过。
可性能没变好，因为**换存储没换模式**。这直接证伪了"把数据访问收敛到抽象层就能换底座"：

- 包进 `DataStore::query('events')`：**134 ms 一毫秒不少**，只是换了个名字。
- 底下换 DuckDB：解码成本还在，**更慢**。
- 底下换 ClickHouse：每次 pageview 变成一次**跨网络拉一万行**，**灾难性更慢**。

> **抽象层能让存储可替换，但不能让一个错的访问模式变对。
> 顺序反了——先修模式，再谈抽象。**

### 这个模式有多普遍

全仓 **44 处** `json_write(..., array_slice(...))` 的"整批写回"。多数无害（一个 200 条的日志），
但至少两处在热路径上：

| 位置 | 规模 | 何时触发 | 后果 |
|---|---|---|---|
| `lib/CdpSystem.php:184` | 10,000 | 每次埋点 | 已量化：134 ms / 26 MB |
| `lib/FrequencyCap.php:50` `freq_log()` | **20,000** | **每次触达** | 群发 1,000 人 = 读写 2,000 万条记录 |
| `lib/MailCampaign.php:72` | 20,000 | 每次统计写入 | 同类 |

`freq_log()` 尤其危险：它在**群发链路里逐个收件人调用**，
每次把 2 万条 JSON 读进来、append 一条、再全量写回。这是 O(n×m)。

## 三、触发器标定错了：墙不在 500 万，在现在

文档的升档触发表说 events > 500 万才进 Tier 2。但按上面的实测：

| events 行数 | 单事件开销（估） | 状态 |
|---|---|---|
| 1 万 | ~130 ms | 已经不合理 |
| **52 万（当前生产）** | **134 ms / 26 MB** | **正在撞** |
| 500 万（文档的触发线） | ~134 ms（读窗口固定一万，不随表长） | 早就撞过了 |

关键在于：这个开销**不随表增长**（读窗口固定 10,000），所以它**不会先给你预警再撞墙**——
它从第一万条事件起就一直是满额的错。量化触发器是好机制，但**这次量错了对象**：
该量的不是"表多大"，而是"单次写入摊了多少读"。

## 四、DataStore 这个抽象的形状不对 🟡

方向（让存储可替换）对，形状（一个泛化查询层）不对。

```php
DataStore::query(string $type, array $filter = [], array $opts = []): array
```

这个签名要同时盖住 JSON 文件和 SQL，只有两个结局：

1. **取最小公分母**——表达不了 join、聚合、窗口、FTS5 全文。于是真正复杂的模块
   （CDP 分群、SearchIndex、CommissionPolicy 结算）**绕过它直接写 SQL**，散落原样回来，
   只是多了一层空壳。
2. **把 `$filter` 长成查询语言**——那就是一个 ORM，也就是一个框架。
   而"无框架单体"是这个项目写在 `README.md:411` 的身份认同。

再算笔账：**1,389 个调用点**的迁移，是几个月的工作量、几百处回归风险，
而收益（换存储）只在一个**目标用户永远到不了的规模档位**才兑现。
这是典型的"为想象中的 Tier 3 抵押掉真实的 Tier 1"。

**该建什么**（第七节 L2 展开）：不是一个泛化 DataStore，而是

- **`EventSink`（文档已有，这个是对的）**——只写、追加、无需查询泛化。
  接口是 `record()` 不是 `query($filter)`，所以它**真能**跨 SQLite→DuckDB→ClickHouse。
- **按数据域的 Repository**——`ProfileRepo::topByLtv(10)`、`OrderRepo::unsettled()`，
  手写方法名说人话，内部随便用全量 SQL/FTS5。可按模块逐个迁、永远长不成 ORM、
  不违背无框架。

## 六、演进的轴可能选错了：垂直 vs 细胞

文档的 Tier 1→2→3 是一条**垂直**路径：*一个实例越长越大* → PG + ClickHouse + 服务拆分。
这是 2015 年那套 SaaS 扩容剧本，没错，但**跟这个产品自己的世界观不一致**。

产品的主张（VISION / AUDIT-06 的 OIA）是：**一人公司、超级个体、零门槛、数据 100% 本地可控**。
那推到规模，形态是**细胞式（横向）**的：

| | A · 垂直（文档默认） | B · 细胞（与 OIA 一致） |
|---|---|---|
| 形状 | 1 个实例，10 亿行 | 10,000 个租户，每个 10 万行 |
| 存储 | PostgreSQL + ClickHouse | 每租户一个 SQLite（`data/<tenant>/`） |
| 难点 | 分片、副本、查询优化 | 供给编排、资源隔离、控制面 |
| 跨租户智能 | 一张大表直接 SQL | **联邦聚合**（`FederatedGrowth` 骨架已在） |
| "数据本地可控" | 破功 | 保住 |
| 需要 ClickHouse 吗 | 需要 | **不需要** |

文档在 Tier 3 表里写了一行"每租户独立 `data/<tenant_id>/` → 天然隔离"——
**这一行就是 B**，但紧接着的几行（PG 主库、ClickHouse 事件管道）又是 A。**两条路混在一张表里。**

我倾向 B，理由不是技术偏好，是一致性：B 让 `FederatedGrowth`（T2-12）
从"隐私骨架"变成**主架构**，让"数据可导出"从合规话术变成**结构事实**，
也让"零门槛参与"在成本上真的成立（开一个租户 = 建一个目录，不是加一片分片）。
而 A 会让产品在长大的过程中，把自己赖以差异化的每条主张逐个放弃。

**这一条现在只需要决定，不需要实现。** 但不决定，L2 的抽象就没法定形——
B 不需要 ClickHouseAdapter，A 需要。
